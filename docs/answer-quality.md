# 内容选择问答与质量基线

2026-10-14，用户在查找入口引用对比文章，询问“帮我找出一款支持中文并且支持克隆的模型”，实际只得到资料数量和两个节选。本文记录通用修复与可重复验收，不保存用户笔记、生成答案或推理正文。

## 原因

保存的请求为 search 模式，并明确引用一篇文章。前端已经将带引用的追问交给本地问答接口，但本地规划仍选择 search，没有进入生成。另一个执行缺陷是 ChatService 会再次用开头动词识别查找，即使通过校验的计划已为 answer，也会被改回仅检索。实际 API 回归连续两次复现该缺陷，中文模型、数据库和英文住宿三个主题都只返回资料数量；显式 answer 合同同样被覆盖。

规划提示中的查找入口优先原文与内容选择规则存在冲突。真实质量检查还发现 2B 模型在关闭推理时会遗漏肯定属性，或被名称和首个条件误导；只检查回答有没有一个名称，无法证明条件正确。

## 通用处理

执行层按校验后的 QuerySpec 操作执行，旧开头动词规则只作未解析请求的回退。文字形式不覆盖已选定的回答工具。直接检索、精确字段查找、显式 search、read、统计和媒体处理继续通过原有工具及权限边界执行。

本地规划遇到候选文档上下文且允许回答时，先作有界的结果目标判断，再构造查询。判断只接收问题、标题、文件名、路径和是否明确引用，不接收正文或真实资料 ID。内容选择、比较和问答确定为当前资料回答时，编译成经过领域校验的 answer + use_context + full_document；其他情况继续原有完整 QuerySpec 规划。非法或截断目标不猜测、不扩大范围、不回退云端。QueryService 仍校验成员身份、明确引用交集和日期约束。

本地与显式云端规划共享内容选择语义：区分查找资料身份与依据资料选择对象，保留全部条件和条件关系，不把文中对象属性伪装为目录字段。生产代码没有某款声音模型、特定文章标题或原问题的处理分支。

本地模型运行器由全局禁止推理改为按模型模板自动识别；内容目标判断和回答启用推理，复杂查询字段规划保留直接 JSON 输出。运行程序以 deepseek 格式将推理与正文分开，并限制推理预算为 256 tokens；目标判断总输出上限 512、回答总输出上限 1536，推理也消耗总输出预算。tokenizer 预检使用与实际请求一致的模板开关。生成端只发出最终 content，不把 reasoning_content 写入聊天、来源或记录。

推理结束但没有最终内容不能视为成功。生成器只在尚未发出任何非空答案时，用相同本地模型、历史和证据关闭推理重试一次；第二次仍为空则返回 local_empty_answer。已发出的答案不重放、不拼接另一版本，网络错误不触发这个重试，云端提供方始终不参与本地恢复。只有空白的前导输出会等待有效内容，正常回答原始空白保留。

## 可重复质量检查

运行以下命令会使用真实本地权重，在临时独立知识库导入三份明确为合成的对比资料，不写生产资料或会话，不调用云端：

```bash
uv run --project backend --extra embedding --extra ocr python scripts/check_answer_quality.py \
  --model-path /完整路径/模型.gguf \
  --embedding-path data/models/embeddinggemma-2 \
  --output /tmp/answer-quality.json
```

可以用 `--case voice_two_conditions`、`database_two_conditions` 或 `hotel_two_conditions` 单独重放。检查首个命名候选是否正确、当前资料范围和完整原文、生成位置、引用编号、错误与截断，并排除“提到正确名字却声称无法选择”的回答。失败以非零状态退出，记录仅含布尔检查、操作类型、长度和时间。评估器自身有错误候选、错误编号和拒绝支持选择的回归。

该名称/引用检查是质量信号，不能证明整段解释的语义归因正确，也不能证明任意多轮、大库或复杂条件都已正确。三组示例有意提供一项同时满足条件的候选，以及分别只满足一项的干扰项；英文问题覆盖相同条件关系，不用它声称所有语言能力一致。

## 真实问题重放与剩余边界

在用户语料的临时隔离副本使用当前配置的 MiniCPM5 2B 重放原问题和明确引用。最终事件是本地 answer，依据只有原引用文章的完整原文，首个识别到的候选属于文章明确支持中文和克隆的选项，引用合法且未截断。最终一轮约 24.75 秒，包含准备与本地生成，回答 329 字符；不作为统一性能保证。未打印原文、推理或回答内容，也未修改已有错误回答。

进一步按客户端历史预算带入原会话的 10 条消息重放，仍返回本地 answer、原引用完整原文及合法引用，首个识别候选满足两项条件，无错误或截断；该轮 22.08 秒、106 字符。两轮采样不同，记录分别保留，不能用单轮结果推断所有后续回答质量。

全量 468 项测试（164 TypeScript、304 Python）、类型与静态检查及构建通过。回归覆盖已校验计划的执行优先级、不同主题/语言的选择、目标规划合法性、推理与最终内容分离、空回答恢复及终止错误；三组真实权重质量检查通过。

验证中确实经历了规划误分类、条件漏判、推理截断和最终回答为空，未删除失败用例。保留的跨主题基线用于观察这些问题是否复发；最终验收报告见 [本地质量报告](answer-quality-acceptance.json)。

每次模型采样仍可能变化。启用推理和空回答恢复会增加等待时间；当前输出预算内的长分析仍可能截断。缺少某项事实应说明当前依据不足，不能擅自补全。正式选择新模型、跨模型对照和更广泛真实问题集仍需独立验收。

## 2026-10-15 日常选择与资料不足

将质量场景扩展到七组：原来的三个正向选择，加上正确选项在末尾、没有同时合格的候选、关键能力未记载，以及真实调用两轮 API 的附加条件追问。追问先用明确引用完成首轮，再将实际生成的问答和来源作为 `history`、可选 `context_document_ids` 传入第二轮，不再用手工指定第二轮引用替代上下文承接。它验证 API 层行为，不代表浏览器交互和任意长度会话均已验收。

扩展检查时发现两个问题。评估器曾允许“先推荐不合格对象、后列出其缺点”的矛盾回答通过；评估回归连续两次失败，修正后必须明确说明无合格选项，并排除这类推荐。真实 MiniCPM5 2B 在信息缺失场景中连续两轮只给 7 或 15 字符的概括性拒答，没有对象、缺失条件或引用。仅追加解释要求仍失败；移除回答要求末尾的固定拒答短句并明确缺失信息的呈现后，解释恢复，但仍捕获过遗漏引用，未将中间结果作为通过记录。

生成要求按证据状态区分：全部条件有依据才推荐；已知某项不满足就解释不满足项；未记载能力则标明具体待确认信息，不能当作不支持，也不能把不同对象的属性拼成一个合格选项。即使无法选出首选，也要保留已知能力、缺口和支持这些描述的来源编号。规则对所有主题和生成提供方共用，没有对象名称、文章标题或特定问题的执行分支；不伪造引用、不拼装预设答案，不增加云端回退。

质量检查增加无依据推荐、未知误当否定、信息缺口说明及流完成边界。`--case tool_answer_last`、`voice_no_joint_match`、`tool_missing_evidence`、`database_followup_conditions` 可独立重放。检查仍是固定合成资料上的名称、表达和编号信号，可能漏掉语义错误或误拒绝正确改写；模型采样结果与规则测试应分开理解，不能宣称七个场景代表全部日常问答。

最终将重复要求收敛为应用层统一的七条回答规则，放在资料之前，本轮问题放在末尾；明确“支持 / 不支持 / 未记载”的证据状态和追问的条件继承、修改与取消。它是生成指令合同，不是程序对文中能力属性进行真实性证明。调试中把生成随机性降为零，仍复现把未记录能力当成缺失能力的错误；因此没有将该实验改为默认配置，也没有把问题归结为采样即可解决。

最后一轮完整验收为 **5/7，通过状态为 false**，原样保存在 [日常质量报告](answer-quality-daily-acceptance.json)，命令以非零状态退出。末尾候选与附加条件追问没有通过“首个命名候选”检查；它说明没有满足先给明确正确选择的合同，不能仅凭该信号断言最终推荐必然错误。追问首轮通过、第二轮使用真实历史和可选文档上下文，资料范围、完整原文、引用、完成状态和原生标记隔离检查均通过。信息缺失场景本轮通过，不抵消先前已人工复核的未知误判问题，不能声称已稳定解决。

全量 504 项测试（164 TypeScript、340 Python）、类型/静态检查与构建通过。规则测试通过说明检查器和边界行为符合预期，不能替代真实模型质量验收。过程仅使用临时合成资料，没有改动生产笔记、历史会话或云端配置；旧错误回答保留。
